# 版本管理与客户端/服务端兼容性

本文是项目开发与发布必须遵守的约束，从产品正式版本 **1.0.0** 开始生效。
现有 `0.x` 测试版本不追溯获得本文的兼容性保证；发布 `1.0.0` 前必须完成对应机制与验收。
本文描述目标契约，不代表当前实现已经满足该契约。

### 1.0.0 数据基线

`1.0.0` 建立正式数据基线，不承诺读取或迁移 `0.x` 开发版本的历史格式、身份与配置。
在 `1.0.0` 准备阶段删除仅服务于 `0.x` 的旧数据迁移、旧路径/服务标识清理、
历史兼容分支及对应测试，不继续维护开发期遗留格式。
仍作为 `1.0.0` 正式格式使用的数据结构不因其源于 `0.x` 而必须删除或重置。

移除历史处理代码不等于安装时自动删除用户数据；不支持的持久化格式应明确报错，
由发布说明给出重置及重新授权步骤，不得静默清空身份、密钥或配置。
正常断开、退出、卸载、故障恢复、临时文件及当前服务残留清理仍须保留。
从 `1.0.0` 开始产生的正式数据遵守本文后续的升级、迁移与回滚契约。

## 1. 统一产品版本

项目采用统一的 `MAJOR.MINOR.PATCH` 产品版本：macOS client、fnOS server、Go CLI
使用同一套发布编号，同一发布的产物来自同一个 Git commit。
根目录 Go module 跟随源码 Git tag，暂不作为第三个产品独立管理版本。

每次正式发布应提供对应版本的 client 与 server 产物；用户可以分别安装、升级两端。
同一次发布使用相同编号，不要求用户安装的两端编号相同。
Git tag 使用 `vMAJOR.MINOR.PATCH`。已发布版本及其产物不可覆盖；修改产物必须发布新版本。
macOS build number、Git commit 等用于构建追溯，不参与远程兼容性判定。

## 2. 唯一的远程版本准入规则

对 `1.0.0` 起的正式发布产物：

```text
允许使用 = client.MAJOR == server.MAJOR
           且 client.MINOR <= server.MINOR

PATCH 不参与兼容性判定。
```

| client | server | 结果 |
| --- | --- | --- |
| 1.2.3 | 1.2.0 | 允许，同 MINOR 时 client PATCH 可以领先 |
| 1.2.0 | 1.4.0 | 允许，server 保持向后兼容 |
| 1.4.0 | 1.2.9 | 拒绝，要求升级 server |
| 1.2.0 | 2.0.0 | 拒绝，要求升级 client |
| 2.0.0 | 1.9.9 | 拒绝，要求升级 server |

“允许使用”保证：在运行环境满足要求、授权有效等正常前提下，客户端在其发布时
已经提供的功能能够在该服务端上正常使用。包括授权与有效会话恢复、设备注册、
配置获取与同步、该客户端已有的连接路径、断线及服务端重启后的恢复、主动断开与清理，
以及设备撤销、权限不足、授权过期等错误处理。

该保证不要求旧 client 获得未来新增功能，也不保证解决网络不可达、上游接口变化等
外部问题。新 server 必须继续接受旧 client 的请求，保留其依赖的字段、语义与行为，
并返回旧 client 能处理的响应。

本项目不要求跨 MAJOR 兼容，不采用逐功能能力协商。client MINOR 高于 server 时，
整个连接被阻止，即使用户暂时不使用新功能，也必须先升级 server。
开发构建、预发布版本和 `0.x` 不自动获得上述正式版保证。

## 3. 版本递增规则

### PATCH：可独立安装的兼容修复

client 或 server 的问题修复、性能改进及打包调整，在不改变兼容契约时升级 PATCH。
必须同时满足：

- 不增加对另一端的新要求。
- 不删除或改变已有协议语义。
- 不要求另一端安装某个 PATCH 才能正常使用。

例如 client `1.2.5` 必须搭配 server `1.2.3` 的设计不允许出现；新增服务端要求应通过
新的 MINOR 表达。安全修复同样遵守版本准入规则，不得暗中增加最低 PATCH 限制。

### MINOR：兼容新增功能

新增功能升级 MINOR。client 依赖 server 新增接口、字段或行为时，必须升级 MINOR，
并发布实现这些要求的对应 server；该 server 仍须支持本 MAJOR 内所有较低或相同
MINOR 的正式 client，不得要求旧 client 同步升级。

纯客户端新增功能若升级 MINOR，同样适用版本准入规则，并应发布对应版本的 server，
即使 server 没有新增协议实现。不得通过例外判断放行较高 MINOR 的 client。

### MAJOR：允许破坏兼容性

删除旧协议、改变已有语义、取消旧 client 支持，或引入不满足既有升级契约的数据与
运行要求时，升级 MAJOR。清理历史兼容实现也必须通过新 MAJOR 完成。
内部重构本身不要求升级 MAJOR；保持外部契约的重构可按实际变化使用 PATCH 或 MINOR。

MAJOR 不同时要求用户升级 MAJOR 较小的一端；不承诺跨 MAJOR 桥接或任意升级顺序。

## 4. 协议实现约束

- server 在固定的 `/version` 入口及 bootstrap 返回 `serverVersion`，HTTP/relay 响应
  保留 `X-FnCPN-Version`，client 请求携带 `X-FnCPN-Client-Version`。最小版本识别入口、版本字段和
  错误表达跨 MAJOR 保持可识别，使旧 client 能准确拒绝新 MAJOR 的 server。
- client 在设备注册与网络配置之前执行版本准入检查；server 重启或连接恢复时重新检查。
  fnOS 网关认证先于应用版本读取；版本请求因 token 失效被拒绝时，先恢复原生会话，
  再重试版本检查。认证流程不依赖 FnCPN 版本通过，认证失败不能被当作版本不兼容，
  会话恢复成功也不能替代版本准入。
- 版本入口返回 404 时，报告 `SERVER_UNAVAILABLE`，提示在 fnOS 安装或启动 FnCPN；
  不将其断言为已卸载。停止自动重连、配置监听和旧网络，保留授权与配置，用户修复后
  手动连接重新检查。普通网络超时或网关 5xx 仍可自动重试。
- 不兼容时停止连接，明确显示两端版本、原因和需要升级哪一端，不得无限重试。
  无法识别版本或收到无效响应时明确报告协议错误，不得默认放行。
- 同一 MAJOR 的新 server 保留旧接口、字段、类型、单位、含义、默认行为及旧 client
  所需的探测和 relay 行为。增加字段不能导致旧 client 失败。
- client 忽略未知响应字段，同时校验必需字段、取值及安全语义。server 可以严格校验
  请求；新 client 所发送的新请求要求必须由对应 MINOR 的 server 支持。
- 远程兼容性使用产品版本判断。本地 IPC 版本和持久化 schema 版本独立管理，
  不与产品版本联动递增，不以本地 IPC 版本替代远程版本准入规则。

## 5. 本地组件及数据升级

App、daemon、privileged daemon 作为安装单元成套升级，不保证任意历史本地组件组合。
安装流程负责处理旧进程退出和新进程启动；检测到组件不匹配时提示完成更新或重启组件。

同一 MAJOR 内，任意较旧正式版直接升级到较新正式版，应保留有效身份、设备关系、
配置和用户连接意图，无须逐个安装中间版本。不得因普通更新无故要求重新授权或注册。
数据迁移应在提交前保留可恢复备份，失败不得留下半迁移状态。

不保证旧程序能读取新程序写入的数据。回滚应恢复升级前程序及配套备份，
旧程序必须拒绝不支持的 schema，避免误读或覆盖。跨 MAJOR 的迁移路径与限制必须
在发布说明中明确，不自动获得同 MAJOR 的直接升级保证。

## 6. 发布验收

从 `1.0.0` 起，将本文作为发布门槛：

- 保留历史正式产物、版本信息与协议样本，使用真实历史实现验证兼容性。
- 候选 server 验证同 MAJOR 内所有已发布 client；候选 client 验证同 MAJOR 内
  所有 MINOR 不低于自身的已发布 server，以及当前候选 server。
- 特别覆盖同 MINOR 下 client PATCH 领先 server，以及旧 MINOR client 连接
  新 MINOR server 的组合。仅运行当前源码的测试不能证明历史版本兼容。
- 验证拒绝更高 MINOR client、拒绝不同 MAJOR，以及提示方向准确。
- 验证核心连接流程、重连与历史数据直接升级；兼容性回归应阻止发布。
- 发布说明记录版本、commit、变更类型、升级要求和数据迁移或回滚限制。

`1.0.0` 发布前需要修正现有严格响应解码、远程版本检查及本地/远程协议版本耦合等
问题。不得仅修改版本号，就宣称当前实现满足本文保证。
